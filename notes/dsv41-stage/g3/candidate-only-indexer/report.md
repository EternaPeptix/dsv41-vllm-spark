# Candidate-only prefill scoring: local implementation

The requested substantial change is implemented in `candidate.patch`: the late consumer indexers **24, 28, 32 and 36** score packed candidate positions using one call to the existing FP8 DeepGEMM implementation. The default is off. This is an exactness qualification candidate; **GPU bitwise equivalence and performance remain untested**. No cluster mutation, GPU import, benchmark, inference, build or service action occurred. The only cluster action for this target was a bounded existing-file byte capture at 17:33:22 UTC; all subsequent work was local.

## What changes

For each admitted query, the new pack kernel copies 2,048 candidate blocks × 8 FP8 K rows and FP32 scale bits into a disjoint 16,384-row interval. A single native compressed-output call (`max_seqlen_k=16384`, `clean_logits=False`) computes candidate scores. An integer atomic scatter writes the scores into the **same logical width and padded row stride as the original dense logits**, initialized to negative infinity. The original native `top_k_per_row_prefill` and CANON remain unchanged. Full-width selection avoids assuming that compact coordinates preserve threshold ties or NaN selection behavior.

The patch changes three paths: the sparse indexer caller, an optional keyword in the DeepGEMM wrapper, and the new `candidate_prefill_fp8.py` module. It retains source-20 scoring/publication, all persistent index-K/cache writes, the original dense gather and its lifetimes, candidate ownership, top-k output and downstream attention order. The stock wrapper path is unchanged when the keyword is omitted. This patch is based on fresh installed sources; it is not an implicit composition with previous P4/P5/R17 candidates.

Admission requires both `DSV41_CANDIDATE_PREFILL_FP8=1` and `DSV41_TOPK_CANON=1`, the pinned model topology (32 heads × 128 dimensions, source 20 and consumers 24/28/32/36, ratio 1), FP8/FP32 metadata, at most 128 query rows, K width 131,072–1,048,576, no decode, no PCP and DCP=1. Candidate publication and MXFP4 routes fall back. Exact ordinary tensor/layout and JIT/mode controls are checked. NONE and PIECEWISE contexts are supported **only outside actual stream capture**; the captured indexer already has `@eager_break_during_capture`. The actual breakable-graph replay hit must still be observed. Foreign or short configurations fall back. The standalone primitive is not a substitute for this caller guard.

## Data movement and arithmetic boundary

The CPU checks execute the actual new pack/scatter source and the actual old flag/mask kernels. Negative candidates are ignored; duplicate candidates retain set semantics. The stock unusual edge rule is preserved: any nonnegative block whose first position is beyond width sets the final logical column, subject to the row's causal interval. Raw uint8 K and int32 scale copies retain every bit; invalid slots are zero-filled and never scattered. Candidate rows/indices and all inputs remain unchanged. Integer widening occurs before large candidate-ID arithmetic.

Native source shows the same four MMA steps for head dimension 128, head accumulation, K-scale multiplication and XOR additions 1 then 2, with no reduction across K positions. The compressed specialization changes output addressing. The installed kernel-header hash matches the local build-source kernel header; the host API/source is corroborating evidence, **not a complete matching-binary or current dispatcher attestation**. Different tiling/specialization/compiler lowering can change floating results. The GPU qualifier therefore checks every valid compact score, including duplicate copies, against the corresponding original dense score bits. Final scattered equality alone would not prove the duplicate-store premise.

The candidate is restricted to canonical output. Raw native top-k order may be nondeterministic; the harness records raw differences and requires repeated baseline canonical sets to be stable before accepting a candidate match. It does not silently qualify CANON-off deployment.

## Work and resource model

The historical trace's roughly 87 ms includes source 20. Four consumers account for **44.6160 ms logits + 16.9348 ms top-k + 10.6109 ms masking = 72.1617 ms** in the cited late segment; flags/gather bring the subtotal to 77.4139 ms. These are saved profile stage sums, not an A/B result or automatically removable latency. This arm replaces the 44.6 ms scoring stage and the mask/flags work with pack, smaller scoring, full-output initialization and scatter. It retains full-width top-k and gather. The saved author's ~2-second/1M projection is not independently measured here.

For the actual 32-head shape, native BLOCK_Q is four. Disjoint per-query intervals make each four-query tile score a union of four 16K intervals: **four times useful candidate score work**, not a one-candidate-score-only ideal. At M=128 and N=1,048,576 the position-pair count model is 8,388,608 versus 134,217,728 (16× fewer); it is about 14–15× at the late-profile context, whose exact kernel extent must be recorded separately from its 942K timeline label. Pack traffic, irregular reads, atomics, output initialization, native scheduling and launch costs can erase part or all of a gain. No bandwidth reduction or speedup is claimed.

At 128 rows, packed K plus scales occupy **264 MiB**; IDs plus compact scores add **16 MiB**. The profiling allowance is **293,733,376 bytes (280.126 MiB)** including bounds and output row-padding allowance, coexisting with the original dense logits and gather storage. It changes memory reservation/peak and possibly startup OOM behavior. Large 16K-query packing is expressly excluded. The new kernels launch 128-slot packing tiles and 512-slot scatter tiles; there is one native score call, not 128 Python score calls. N, candidate stride and output stride do not specialize Triton kernels, including alignment, so changing context width is intended to reuse warmed pack/scatter variants. Actual cache identity and post-warmup compile attempts are checked by the GPU harness.
